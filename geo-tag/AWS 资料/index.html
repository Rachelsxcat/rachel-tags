Business challenges

Listing 运营面临的六个问题

广告在为商品买流量，但商品页面写得好不好、AI 购物助手会不会推荐它，目前缺少系统的判断。

01广告在花钱，页面没人系统诊断

ACOS 偏高的单品，问题可能出在页面没写清楚，而不是出价。哪一句该改、为什么，目前靠运营经验判断。

02AI 购物助手推不推荐，看不见

越来越多买家直接问 Alexa for Shopping。它推荐了谁、我们排第几、为什么没推荐我们，现在没有观测手段。

03买家声音分散在各处

评论、退货原因、AI 助手里的追问、广告搜索词、产品参数分属不同系统与部门，需要人工拼接才能得出结论。

04目标人群与真实买家可能不一致

市场部的人群定位缺少数据验证。写给错的人群，内容改得再好也难被推荐。

05人工改写容易出错

参数凭记忆填写容易写错，绝对化表述、超长标题会触发平台规则；逐条人工核对耗时，且难以保证每次都查全。

06难以对齐 Amazon 的「好 Listing」标准

作为单一卖家，只能看到自己的商品与有限的竞品，对 Amazon 认可的 Listing 写法缺少可对照的标准，规则也在持续调整。

方案要做的：以广告单品为起点，把卖家视角、买家视角、官方视角放在一起，在一个工作台里完成诊断、改写建议与 AI 可见度观测，每条建议都有依据。

Solution

方案：一个按广告单品工作的 Listing 运营工作台

运营选一个在投的广告单品，工作台把卖家、买家、官方三个视角的信息放在一起，给出有依据的改写建议，并持续观测它在 AI 购物助手中的表现。

01优化建议

逐字段给出改前改后，每条注明依据与回应的视角；生成前后自动检查平台规则。对应痛点 01、05、06。

02AI 可见度

由真实买家数据生成画像，按画像向 AI 购物助手提问，看推荐了谁、我们排第几、为什么。对应痛点 02、04。

03商品知识

把评论、退货、追问、搜索词、产品参数与平台规则汇总到同一商品上，结论可追溯。对应痛点 03。

边界：只出建议，不写回 Amazon；同一套流程适用于所有单品，不为单个商品定制。

Highlights

方案亮点

从广告单品出发，同时对照卖家、买家、官方三个视角；每条建议都有可追溯的依据。

业务 01三个视角合一

卖家想打的人群与卖点、买家真实的需求与反馈、Amazon 官方规则与业界运营实践，放在同一套判断里。

业务 02画像驱动的 AI 可见度

把卖家定位与买家真实需求对齐成画像，按画像检验 AI 购物助手推不推荐、排第几、为什么。

业务 03改写不出错

参数只来自产品主数据，平台规则在生成前后自动检查，运营只需终审。

技术 01商品知识库

多源数据连成商品、卖点、场景、人群、反馈之间的关系，Agent 顺着关系回答「改哪一句、为什么」。

技术 02建议可追溯、不编造

每条建议都能追到来源数据；参数来自产品主数据，平台规则在生成前后校验。

技术 03非定制扩展

同一套流程适用于所有单品；加品类、加站点只需补齐数据与业务输入，不用改程序。

Highlight · Three perspectives

业务亮点：卖家、买家、官方三个视角同时对照

单一卖家只能看到自己想说什么。方案把三方的判断放在一起，建议既符合品牌意图，也回应买家需求，并对齐 Amazon 认可的写法。

卖家视角我们想卖给谁、主打什么

市场部的目标人群与核心卖点、产品主数据中的真实参数。确保建议不偏离品牌定位，参数不出错。

买家视角买家实际在意什么

评论、退货原因、AI 购物助手里的追问、广告搜索词。找出买家最常问、页面却没写清的地方。

官方视角Amazon 认可什么样的 Listing

Amazon 平台规则与品类属性要求，结合业界运营实践与内部运营专家的经验沉淀成知识库，作为「好 Listing」的对照标准。

带来什么：每条建议都能说明它回应了哪一方：符合品牌定位、回答了买家的问题、满足平台与业界标准。
AWS ProServe
Highlight · Persona-based visibility

业务亮点：按真实买家画像检验 AI 购物助手

AI 购物助手会根据提问者的身份与场景推荐不同商品。不带画像的测试结果没有参考价值。

01画像来自真实数据

从评论、追问、退货原因与广告搜索词中归纳人群、场景与关注点，再与市场部的目标人群对齐。

02发现定位偏差

例：市场部主打「租房年轻人」，买家真实提问中「换新业主」是前者的 3 倍。两类人群都纳入测试。

03看到推荐结果与理由

每个画像下，AI 助手推荐了谁、我们排第几、推荐理由是什么；没推荐我们时，推荐了哪些竞品。

带来什么：优化方向从「写得更好」变成「写给对的人」，并能看到每类人群下的推荐变化趋势。

Highlight · Scale without customization

非定制扩展：什么情况靠配置就能扩，什么情况算定制

同一套流程适用于所有单品。新站点、新品类只要按模板补齐数据与业务输入就能接入，不需要改程序；需要为某个商品、品类或站点单独开发的，算定制。

情况类型需要做什么
US 再加一个品类，例如从油烟机扩到微波炉非定制提供该品类的产品参数、目标人群与标杆样本，系统按同一套流程运行
新增一个站点，例如 UK、DE非定制完成账号授权，提供当地语言的标杆样本与审核人；平台规则按站点配置
一个品类里新上架的单品非定制自动纳入，无需额外开发
换一个大模型，或 Amazon 调整字符上限、禁用词非定制更新配置与规则表
某个爆款要单独一套写作规则或单独的页面定制破坏「所有单品同一套流程」，后续每次升级都要单独维护
某站点的 AI 助手形态完全不同，需要另写一套测试方式定制超出原有测试流程
要求接入 ieCom 之外的新系统，或自动写回 Amazon定制超出项目范围
为什么重要：非定制扩展的成本主要是业务输入，可以预估；定制会让方案分叉，每多一个分支，后续维护与升级成本就多一份。定制需求另行评估。

Measuring impact

效果验证方案：交付质量可承诺，其余只看趋势

文案改动对销量的影响会被价格、广告、库存、季节和平台模型更新共同作用，无法单独归因。因此只有第一层交付质量作为验收依据，其余三层记录趋势，并与同期事件并列展示。

层级指标数据来源怎么判
1 交付质量 · 可承诺平台规则满足率；必填属性完整度；建议附证据比例；评测集得分Agent 产出 + 品类属性模板规则满足率 100% 为验收项，其余为参考
2 AI 可见度 · 过程指标画像命中率（Rufus，多次采样取比例）；商品信息摘要的卖点覆盖；高频追问已被 Listing 回答的比例项目自动测试与抓取改前 / 改后同一套画像与问句复测，记录趋势
3 搜索与流量 · 结果指标本单品的搜索曝光、搜索点击率、详情页浏览量Brand Analytics · Search Catalog Performance；VC Retail Analytics · Traffic记录趋势，并列标注同期价格、广告、库存变化
4 转化 · 滞后指标转化率（发货量 ÷ 浏览量）；同词广告转化率；退货率VC Retail Analytics；广告一期数据；退货报表记录趋势，不作为承诺，也不归因到内容改动
基线与观察期

改前 4 周为基线；改后第 3~6 周为观察期，留出平台重新索引的时间

同期事件并列

售价、广告预算、库存、竞品断货与大促一并记录，与指标放在同一时间轴上

不做归因

过程与结果指标只说明「改动前后发生了什么」，不推断「是改动带来的」

剔除干扰周

例如大促、断货或丢失 Buy Box、大幅调价或调整广告预算的周。具体排除哪些情况、阈值多少，在项目中由美的业务方与 AWS 共同定义并签字

行业做法参考：Listing 优化服务商通常用转化率、自然流量与搜索曝光展示效果；1P 卖家的浏览量与转化率来自 VC Retail Analytics 的 Traffic 与 Sales 报表。

Scope & expectations

预期边界：项目让商品页写得更好，不保证卖得更多

Listing 优化是市场化行为的一部分，结果由平台、竞争与运营共同决定。项目交付的是可验证的诊断、建议与评估能力，不承诺销售指标。

项目能做到
  • 按广告单品诊断 Listing：缺什么、该改哪一句、依据是什么
  • 生成符合平台规则的改写建议，参数来自产品主数据
  • 持续观测 AI 助手与自然搜索对单品的呈现变化
  • 用统一口径评估每一批改动的过程指标与结果指标
项目做不到
  • 保证销量或排名提升：Listing 只是成交的一个环节
  • 直接改写 Amazon 页面：采纳与上架由美的落实
  • 控制 Amazon 的排序与 AI 推荐模型：平台会自行更新
  • 为单个商品定制运营内容或流程：会让方案无法扩展，不在范围内
  • 覆盖图片、视频与语音购物：属于探索项
市场效果受外部因素主导

价格、竞品动作、库存、评论星级、广告预算与季节对销量的影响通常大于文案。内容写好了，买家看到商品页时更容易选择它，但能不能被看到、最终买不买，还取决于这些因素。

平台AI 助手仍在变化

Rufus 已并入 Alexa for Shopping，各站点所处阶段不同；同一问题多次回答也会不同，命中率只能按比例统计、站内纵向比较。

时间见效有滞后

平台重新索引与 AI 摘要更新需要时间，改动后 2~6 周才能观察；单品销量小时需要更长观察期才有统计意义。

数据数据决定诊断深度

产品主数据与卖家意愿未补齐时，Agent 只能给出较浅的建议；退货原因、提交版 Listing 缺失也会削弱诊断。

How to set milestones

设定里程碑的四条原则

知识库最容易返工，里程碑要尽早暴露风险，而不是把验证都压到最后。

01先签字，后开工

数据口径与知识结构签字后再改，图谱及依赖它的工具都要重建，因此签字就是每个里程碑的完成标准。

02先在试点范围纵向打通

M1 至 M3 在 US 与 JP 的主营品类端到端跑通，M4 以非定制方式扩展到其余站点，问题暴露得更早、修正成本更低。

03按交付验收，不按业务效果

点击率、命中率等效果指标受平台模型更新与市场影响，作为优化参考指标定期汇报，不作为里程碑判据。

04平台规则必须满足，增量收益只作参考

Amazon 字符限制、禁用短语等平台规则是硬性要求，必须 100% 满足；评测分数与内容带来的增量收益受市场与平台影响，只作为优化参考，不作为验收承诺。

Technical architecture

技术架构：五层职责与关键选择

架构沿用广告一期的数据底座，新增知识层、Agent 层与运营工作台。每一层都可以独立替换，不绑定单一模型或单一采集方式。

层负责什么关键选择
数据接入与治理广告与搜索数据复用一期管道；页面、AI 助手回答由抓取任务定时采集，失败时显式中止并告警复用 S3 + Glue + Step Functions；抓取跑在 Fargate，带节流、重试、熔断

Agent 层编排诊断、生成、规则校验与可见度测试Strands Agent 部署在 Bedrock AgentCore；模型统一使用 Claude Opus 5.5（Bedrock），可按需替换
服务与应用运营工作台：广告单品、优化建议、当前内容、AI 可见度、知识图谱、效果API Gateway + Lambda；Web 应用 CloudFront + S3；作为服务提供方只消费美的 IdP 签发的 access token，不另建账号与权限体系
运维与安全全部部署在美的 AWS 账号；数据不出账号；调用量、费用与失败率可观测CloudWatch 监控与告警、KMS 加密、Secrets Manager、WAF；prompt 与回答缓存降低时延与费用
需与 IT 对齐：现有主数据平台或图数据库能否复用；ieCom 侧按接入方案适配的对接人与排期；身份令牌字段与出网方式。

Model access

模型接入：开发期由 AWS 提供，切换自有通道需满足 Agent SDK 条件

开发与验收阶段，Agent 运行在 Strands + Bedrock AgentCore 上，模型通过 Bedrock 调用。美的现有 AIMP 只提供 chat completions 接口，无法承载 Agent 所需的工具调用与多轮编排；如需切换到美的自有模型通道，需由美的提供满足以下条件的 Agent SDK。

能力最低要求为什么需要
工具调用模型能按 JSON Schema 发起工具调用，并接收工具结果继续推理；支持一轮内多次调用Agent 的抓取、查询、规则检查都靠工具调用完成
多轮会话状态消息里可携带系统提示、历史对话、工具调用与工具结果，顺序与角色不丢失一次诊断通常要十几轮工具往返
结构化输出可按指定 Schema 返回 JSON，失败时有明确错误建议、证据、规则检查结果都要结构化落库
长上下文与多模态上下文不少于 200K token；支持图片输入商品知识、评论与页面截图需一并送入
流式与推理控制支持流式返回；可控制推理强度与最大输出长度工作台交互体验与费用控制
缓存与用量回传支持提示缓存；每次调用返回输入、输出、缓存 token 数成本核算与优化依赖用量数据
稳定性明确的并发与限流额度、超时、错误码与重试语义；模型版本可固定离线批量任务与验收结果可复现
鉴权与可观测服务间鉴权方式；调用链路可追踪（如 OpenTelemetry）排障与审计
数据约束调用数据不用于模型训练；数据处理地域可确认美的数据安全要求
边界：AWS 负责把 Agent 适配到满足上述条件的 SDK；SDK 不满足条件时，开发与验收继续使用 Bedrock，适配工作走变更评估。

Critical dependencies

三件事决定这条线能否按计划推进

建议在合同启动后的第一周就明确负责人和截止时间。

确认数据

数据与权限盘点、ieCom 自有资产盘点尽可能早完成。目标画像、卖家意愿等业务输入同属数据资产，一并盘点。数据源清单签字前，知识库无法开工。

确认开发物料与成本

开发与验收所需的账号与权限、开发期云资源与模型费用的预估与预算、客户侧各环节的支持人员。物料不到位，开发无法按排期启动。

关键节点签字与业务配合

数据口径、知识结构定义、「好 Listing」标准与标杆样本等关键结论需按里程碑签字，业务方需持续参与评审与试用。未签字前，双方对「好内容」缺少共识，评审容易反复。

各站点 AI 购物助手处于不同迁移阶段，且平台模型会自行更新。效果观察需要记录同期价格、广告与大促等事件。

Scaling risks & customer responsibilities

跨站点、跨品类的交付风险与客户职责

试点范围：US（北美站）与 JP（非英语主流站点）的主营品类。技术架构按站点、品类配置化，扩展的主要成本在业务输入与平台差异。

风险点为什么不能自动扩展客户职责
跨站点 · AI 购物助手各站点 Rufus / Alexa+ 处于不同迁移阶段，部分站点缺少入口；同一套测试集在不同站点的命中结果不可直接比较确认各站点的入口形态；命中率只做站内纵向对比
跨站点 · 语言与平台规则按站点原生语言产出；禁用词、标题规则、属性模板与字符上限按站点各不相同，且 Amazon 持续调整提供各语言的内容审核人与标杆样本；内容终审与发布
跨站点 · 账号与页面Vendor Central 与 Brand Registry 按区域 / 站点授权；前台页面、排名、竞品靠抓取，各站点页面结构不同按站点完成账号授权与数据盘点
跨品类 · 业务输入卖家意愿、目标画像、标杆样本与「好 Listing」标准需逐品类整理并签字，无法自动扩展按统一模板逐品类提供并签字
跨品类 · 产品事实各事业部 PIM 字段口径不一，跨事业部扩品类需重新对齐；小众品类样本少，结论不稳定协调各事业部提供产品主数据并对齐口径
范围边界：项目支持「非定制」扩展，即通过配置接入其余站点与品类并抽样跑通；同一套诊断与生成流程适用于所有单品，不为单个商品定制。与试点站点（US、JP）或主营品类不一致、或针对单个商品定制运营内容所带来的工作量，项目内不负责；如需定制，另行评估与报价。
